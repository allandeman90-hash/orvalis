```
TARGET PRODUCT: ORVALIS MMORPG
MIGRATION STRATEGY: incremental replacement of the current Three.js engine
FINAL RENDERER: custom WebGPU backend + WebGL2 fallback
THREE.JS STATUS: legacy/temporary during migration, not final renderer
```

Règles qui en découlent :
- Un seul projet : Orvalis. Pas de moteur séparé qui diverge, pas de portage « big bang » à la fin.
- La version actuelle (Three.js) reste fonctionnelle tant qu'elle n'est pas remplacée.

- L'ancien code Three.js est isolé progressivement ; le nouveau moteur se construit à côté, derrière des interfaces propres.
- Un système n'est remplacé que lorsque son remplaçant est validé ; l'ancienne implémentation n'est supprimée qu'après cette vérification.
- Chaque phase doit livrer un résultat visible/testable DANS Orvalis :
  - Phase 0 → Orvalis démarre avec la nouvelle architecture à côté de l'ancienne.
  - Phase 1 → une zone test utilise le nouveau terrain dans Orvalis (zone de test technique, pas la géographie finale).
  - Phase 2 → cette zone reçoit le nouvel éclairage/fog.
  - Phase 4 → un modèle de personnage Orvalis fonctionne dans le nouveau renderer.
  - Phase 7 → caméra Orvalis fonctionnelle.
  - Phase 8 → personnage Orvalis entièrement contrôlable avec le nouveau contrôleur de mouvement.

## DÉCISION OFFICIELLE SUR LE MONDE (Allan, 2026-10-02)

```
TARGET WORLD: nouvelle world map Orvalis
OLD WORLD: prototype uniquement
WORLD STRUCTURE: plusieurs continents + océans + îles
OLD COORDINATES: non contraintes
CONTENT: réutilisable et repositionnable
WORLD STREAMING: tile/chunk based
EXPANSION: nouveaux continents/maps doivent pouvoir être ajoutés facilement
```

Complément du 2026-10-02 (échelle et bornes du monde) :

```
Vanilla 64×64 map size: REFERENCE ONLY
Orvalis world tile coordinates: UNBOUNDED/SPARSE AT ENGINE LEVEL
Terrain physical scale: CONFIGURABLE
```

- On garde de la spec la TOPOLOGIE : tile = 16 × 16 chunks ; chunk = 8 × 8 cellules, 145 sommets de hauteur, 256 triangles au plus.
- L'ECHELLE PHYSIQUE est configurable : seul `cellSize` est choisi, `chunkSize` et `tileSize` en sont dérivés. Aucun code ne doit écrire 33,333 ou 533,333 en dur, ni dépendre d'un profil.
- Deux profils : `VANILLA_REFERENCE` (cellule 25/6 ≈ 4,1667 → chunk ≈ 33,333, tile ≈ 533,333), référence historique uniquement ; `ORVALIS_DEFAULT` (cellule 4 → chunk 32, tile 512).
- Les coordonnées de tile sont des entiers quelconques, négatifs compris, sans borne. Une map est un ensemble creux `TileCoord → TerrainTile` ; une tile absente n'a aucun coût en géométrie détaillée. Continents, océans et îles d'une grande map peuvent partager le même espace de coordonnées.
- Le générateur de monde / world builder viendra bien plus tard, quand chunk → tile → culling → streaming seront solides.

Ce que cela implique :
- Le monde actuel (carré de 4096 m, 9 zones en grille 3×3, 1024 × 1024 cellules) est un PROTOTYPE. Il ne dicte ni la géographie, ni les dimensions, ni les coordonnées du nouvel Orvalis.
- On conserve les SYSTÈMES et le CONTENU d'Orvalis : noms de zones, lore, factions, monstres, quêtes, villes, ressources, donjons, classes, objets. Leurs positions pourront être entièrement remappées.
- Aucune obligation de préserver les positions actuelles des villes, routes ou points d'apparition.
- Structure cible : `World → Maps (continents) → tiles → chunks`. Chaque continent est une map avec sa propre grille de tiles ; d'autres maps peuvent être ajoutées plus tard sans toucher aux existantes.
- La grille de tiles est une structure technique de streaming, invisible pour le joueur. Les continents ont des formes naturelles ; beaucoup de tiles sont vides ou océaniques (pas de géométrie détaillée pour l'espace intermédiaire).
- Des régions très éloignées doivent pouvoir exister sans remplir l'espace entre elles.
- Le monde définitif n'est PAS à générer maintenant : d'abord les fondations du moteur.
- L'ancien terrain peut servir, au mieux, de zone de test technique.

## STRATEGIE DE VALIDATION (décision d'Allan, 2026-10-04) — REGLE PERMANENTE
Objectif : même fiabilité A LA FIN d'un checkpoint, boucle développement → test → correction de 5 à 30 secondes. La règle « pas de ✅ sans vérification » ne change pas ; ce qui change, c'est QUAND et QUELS tests tournent.

NIVEAU 1 — boucle de développement (après chaque petite modification) :
- `npx vitest run <fichiers de test du système modifié>` (pas la suite complète) ; `tsc --noEmit` (rapide, accepté en entier) ; eslint sur les fichiers modifiés ;
- UN smoke ciblé seulement si la modification est visuelle / runtime : `npm run smoke -- --suite=<nom>` (ajouter `--backend=webgl2` pour aller vite quand le changement est indépendant du backend ; les deux tout de suite si le renderer ou un shader est touché) ;
- INTERDIT pendant le développement d'un Px.y : `smoke:all`, les scénarios sans rapport, les 42 scénarios legacy.

NIVEAU 2 — fin d'un checkpoint Px.y (une fois, quand la fonctionnalité semble terminée) :
- `npm run check` = `tsc --noEmit` + eslint + vitest COMPLET + `legacy:check` + `vite build` ;
- les smokes des systèmes AFFECTES par le checkpoint, sur WebGL2 ET WebGPU (obligatoire avant ✅) ; pas `smoke:all` si le checkpoint ne touche qu'un sous-système.

NIVEAU 3 — validation lourde : `npm run verify` (= `check` + `smoke:all`), réservée à : fin d'une PHASE complète, avant modification importante du legacy, avant fusion / migration d'un système, modification du `RendererBackend` global ou d'un protocole partagé par beaucoup de systèmes, milestone majeur, release.

LEGACY : tant qu'aucun fichier de `src/` n'est modifié, `legacy:check` suffit ; les scénarios legacy complets sont relancés si `src/` change, si une frontière moteur/legacy change, ou avant un milestone majeur.

UNITAIRE vs SMOKE : les deux doivent apporter une preuve DIFFERENTE — test unitaire = logique / math (ex. matrice d'os exacte) ; smoke = intégration navigateur / GPU / rendu réel (ex. l'os est visible au bon endroit à l'écran). Pas de smoke qui revérifie une valeur déjà prouvée par un test unitaire déterministe.

OUTILLAGE (`engine/scripts/smoke.mjs`, réorganisé le 2026-10-04) :
- suites nommées et étiquetées : `npm run smoke:list`. Etiquettes : renderer, webgpu, webgl2, terrain, water, lighting, model, assets, bootstrap, legacy.
- `npm run smoke -- --suite=<nom>[,<nom>…]` (exécutées dans l'ordre donné) ; `npm run smoke:renderer | smoke:terrain | smoke:water | smoke:lighting | smoke:model | smoke:legacy` (par étiquette) ; `npm run smoke:all` = tout + parité dans le même navigateur (`--exhaustive`).
- options : `--backend=webgl2|webgpu|both` (défaut both : WebGL2 dans le navigateur sans adaptateur WebGPU, WebGPU dans l'autre, puis comparaison des deux images) ; `--keep-going` (défaut : ARRET A LA PREMIERE SUITE EN ECHEC, code de sortie non nul) ; `--no-build` (défaut : `vite build` d'abord, pour ne jamais tester un build périmé).
- `npm run smoke` SANS suite ni étiquette ne lance rien et sort en erreur : la validation lourde ne part jamais par accident.
- lancement : en avant-plan, on lit le code de sortie. Plus d'attente fixe (`sleep` arbitraire) ; si un lancement asynchrone est vraiment nécessaire (smoke:all dépasse la limite d'une commande chez moi), on attend la FIN du processus.
- durées mesurées (machine de dev, rendu logiciel) : `--suite=model-skeleton --backend=webgl2` ≈ 3 s build compris ; `smoke:model` sur les deux backends ≈ 7 s ; l'ancien smoke complet ≈ 9 min (surtout les suites terrain).

## SYSTÈME DE COORDONNÉES (décision d'Allan, 2026-10-02)

```
ENGINE COORDINATE SYSTEM: right-handed / Z-up, ground plane = X/Y
LEGACY ORVALIS: Y-up
LEGACY → ENGINE: explicit coordinate conversion at migration boundaries
```

- Dans tout le nouveau moteur : `position = (x, y, z)`, terrain sur x/y, hauteur = z, yaw = rotation autour de Z. Cohérent avec la spec.
- L'ancien Orvalis (Y vers le haut, sol en x/z) n'est converti QU'AUX frontières de migration, par une conversion explicite et nommée. Aucune conversion implicite dispersée dans le moteur.
- Sens des triangles : anti-horaire à l'écran = face avant (`FRONT_FACE = 'ccw'`), sur tous les backends. Le dessus du terrain est la face avant.

Spec de référence : `docs/WoW_Vanilla_1.12.1_RE_Master.md` (9364 lignes, §1–§299).
Règle : une tâche n'est ✅ que si typecheck + tests + contrôle legacy + build + smoke passent (`cd engine && npm run verify`).

## Known problems
- Aucun connu.
- Lint : couvre `engine/` seulement. Le code du jeu actuel (`src/`, `tools/`, `tests/`) n'est pas linté, pour ne pas y déclencher de modifications.
- Bootstrap : le mode legacy est une redirection vers une autre page (deux documents distincts, aucun mélange des deux moteurs). Le jeu actuel n'étant pas modifié, il n'offre pas de lien de retour vers le nouveau moteur : on change de mode par l'URL. En dev comme au build, la page legacy vient de `dist/test.html` à la racine, qui doit donc être construite (`npm run build:prod` à la racine).
- Le site construit (`engine/dist`) pèse ~4,7 Mo, presque entièrement la copie de la page du jeu actuel.
- Scénarios du jeu actuel : environ une heure en rendu logiciel, donc hors de `verify`. Lancés à 4 en parallèle, 24 sur 42 dépassent leurs délais : toujours les lancer un par un.
- Asset manager : vérifié sur HTTP réel avec un petit fichier texte. Pas encore utilisé pour un vrai asset de jeu (binaire, gros fichier, envoi GPU réel) : ce sera le cas avec le terrain.
- Garde-fou HTML : une réponse `text/html` est toujours refusée comme asset. Vérifié contre Vite (dev) et contre le serveur statique du smoke test ; NON VERIFIE contre un hébergeur réel configuré en « SPA fallback ».
- Asset manager : pas encore de limite mémoire ni de politique d'éviction automatique (`evict()` est appelé à la main), pas de priorités de chargement, pas d'abandon réseau réel (un téléchargement annulé va au bout puis son résultat est jeté), pas de nouvelle tentative automatique après un échec. Un téléchargement qui ne répond jamais laisse l'asset en `downloading` indéfiniment.
- La recréation des ressources GPU après une perte de contexte n'est toujours pas faite : l'asset manager garde l'URL de chaque asset mais ne sait pas encore tout re-téléverser.
- Chunk : rendu avec des couleurs de debug par sommet (rouge = x, vert = y, bleu = hauteur). Pas de normales, d'éclairage, de textures ni de trous. Scène et sondes vérifiées avec le profil `ORVALIS_DEFAULT` seulement dans le navigateur ; l'autre profil est couvert par les tests unitaires.
- Shaders : la matrice est appliquée en `mvp × position` dans les deux langages ; la parité WGSL/GLSL est vérifiée par pixels pour ce shader uniquement.
- Overlay : les champs de la spec qui n'existent pas encore ne sont pas affichés (position joueur/caméra, tile courante, tiles chargées, chunks visibles, groupes WMO, M2, ping, entités répliquées). Ils s'ajoutent à `OverlayData` avec les systèmes correspondants. Les bascules de debug (wireframe, chunk bounds, fog…) arrivent avec le terrain (P1.15).
- FPS mesurés en headless : 60 en WebGL2 logiciel, 29 à 57 en WebGPU logiciel selon la charge du bac à sable. Ce ne sont PAS des mesures de performance du moteur ; le smoke test vérifie seulement que les chiffres sont vivants et cohérents (bornes larges : 5 à 240 fps).
- PERTE DE CONTEXTE GRAPHIQUE NON GEREE (WebGL2 `webglcontextlost`, WebGPU `device.lost`). Aujourd'hui : la perte est seulement enregistrée (WebGPU : dans `drainErrors()`), le rendu s'arrête et rien n'est recréé. A traiter quand l'AssetManager saura recréer buffers, pipelines et textures : détecter la perte, recréer le backend (éventuellement avec repli WebGPU → WebGL2), re-téléverser les ressources, reprendre la boucle.
- Backends réels sans test unitaire Node (pas de GPU hors navigateur) : ils ne sont vérifiés que par le smoke test. La logique commune (règles de frame, validation, sélection, scène) est testée unitairement.
- Erreurs de shader : WebGL2 lève une exception à `createPipeline` ; WebGPU ne peut les signaler qu'en différé (`drainErrors()` / console). Différence de comportement connue entre backends, uniquement sur le chemin d'erreur.
- WebGPU en headless : ne fonctionne ici qu'avec Chromium complet en « nouveau headless » + Vulkan logiciel (`--enable-unsafe-webgpu --enable-features=Vulkan --use-vulkan=swiftshader`). ## Technical decisions
- Client seul pour l'instant (pas de monorepo client/server/shared avant la phase 11 ; §289 reste la cible).
- Le nouveau moteur vit dans `engine/` avec son propre `package.json` et son propre `tsconfig.json`. Ne JAMAIS placer de `tsconfig.json` à la racine ou au-dessus de `src/` : esbuild en hériterait et le bundle du jeu actuel changerait (`"use strict"` ajouté — cause trouvée et vérifiée en M0.2).
- Le `package.json` racine fait partie de l'empreinte `sourceHash` du jeu actuel : ne pas le modifier sans reconstruire `dist/`.
- Le nouveau moteur (`engine/src`) n'importe jamais Three.js.
- TypeScript strict, aucune dépendance runtime ; pas de moteur 3D tiers (le renderer suit la spec, pas de PBR).
- Vite 5 + Vitest 2 ; smoke via playwright-core sur le build de production.
- Unités : « unités monde ». L'échelle physique du terrain vient de `TerrainConfig.cellSize` (profil Orvalis : 4). Stockage terrain en float32 (§5).
- Valeurs marquées 🟡 dans la spec : configurables, jamais inventées.
- Math : matrices column-major, vecteurs colonne, repère main droite ; `perspective` prend la convention de profondeur en paramètre (WebGL −1..1, WebGPU 0..1). Le module math n'est pas encore importé par `main.ts` (il le sera à partir de P0.5).
- Boucle : pas de simulation fixe 1/60 s, indépendant du FPS d'affichage ; borne de hitch 250 ms (même borne que le pas d'intégration max cité §199). Le pas de 1/60 s est un choix d'ingénierie, pas une valeur de la spec.
- Terrain : topologie de la spec (16×16 chunks par tile, 8×8 cellules par chunk), échelle configurable, aucune borne sur les coordonnées de tile (le 64×64 de la spec est une référence historique, pas une contrainte).
- Terrain : le sol est le plan (x, y) et la hauteur est z, comme dans la spec et comme `TileCoord {x, y}`. ATTENTION : le jeu actuel est en Y vers le haut (sol en x, z). La conversion se fera à la frontière quand du contenu legacy alimentera le nouveau terrain.
- Terrain : une frontière appartient à la tile (ou au chunk) qui commence là ; intervalles semi-ouverts [k·taille, (k+1)·taille). Les conversions sont corrigées pour être exactement cohérentes avec `tileOrigin`/`chunkOrigin` : origine → indice → origine fait toujours l'aller-retour, y compris pour une taille non représentable exactement (533,333…) et pour le plus petit nombre négatif. La tile donnée par `worldToChunk` est toujours celle de `worldToTile`.
- ECS : stockage par composant en `Map` (simple, pas d'archétypes). A optimiser seulement si une mesure le justifie. Les identifiants d'entité ECS sont locaux ; les identifiants réseau stables viendront en phase 11.
- Rendu : le reste du moteur ne voit que `RendererBackend` et des handles opaques, jamais d'objets WebGPU/WebGL2. L'interface est volontairement minuscule (liste de triangles non indexée) et s'étend étape par étape (index, uniforms, textures, blend, profondeur).
- Parité des backends : `NullBackend`, `WebGL2Backend` et `WebGPUBackend` partagent `FrameGuard` (règles de frame et de durée de vie) et les mêmes validations. Les fabriques réelles sont asynchrones (`create(canvas): Promise`) parce que WebGPU l'impose. Les outils de test (`readPixels`, `drainErrors`) sont dans une interface à part, `RendererDebug`, asynchrone pour la même raison.
- Profondeur : tampon de profondeur sur les deux backends (WebGPU `depth24plus`, recréé au redimensionnement). Par pipeline : `depthTest` et `depthWrite` (vrais par défaut), comparaison « plus proche gagne ».
- Culling : `cullMode: 'back'` par défaut ; face avant = anti-horaire, identique sur WebGPU et WebGL2 (vérifié par pixels).
- Uniformes : un seul bloc par pipeline, nommé `Globals`, binding 0, taille déclarée (`uniformBytes`, multiple de 16). Il ne contient que des `mat4` et `vec4`, pour que sa disposition soit identique en WGSL et en GLSL std140. WebGL2 vérifie que la taille déclarée correspond au shader. Les valeurs sont lues pendant `draw()` : l'appelant peut réutiliser son tableau ensuite.
- Index : toujours `Uint16` (un chunk a 145 sommets). Les valeurs des index ne sont pas vérifiées contre le nombre de sommets (coût) ; seule la plage lue dans le buffer l'est.
- Ordre des sommets d'un chunk : rangées alternées du y le plus bas au plus haut — 9 sommets externes puis les 8 centres des cellules au-dessus (17 rangées). externe (i, j) → j·17 + i ; centre (i, j) → j·17 + 9 + i. C'est NOTRE choix d'ordre : la spec donne les effectifs (81 + 64), pas l'ordre.
- Caméra de test : simple outil œil/cible/haut pour regarder la géométrie. Ce n'est pas la caméra de jeu (phase 7).
- Sélection : ordre WebGPU puis WebGL2. Après un échec, le canvas est remplacé par un clone neuf avant d'essayer le backend suivant (un canvas qui a servi à un type de contexte ne peut pas en fournir un autre). `forceWebGPU` supprime le repli et rend l'échec visible.
- `@webgpu/types` (dépendance de développement, types seulement) : TypeScript 5.9 ne fournit pas les types WebGPU.
- Shaders : chaque shader est écrit DEUX fois à la main (WGSL pour WebGPU, GLSL ES 3.00 pour WebGL2), sans transpileur. Les deux versions doivent rester équivalentes.
- Assets : `httpFetchBytes` envoie `Accept: application/octet-stream` et refuse les statuts d'erreur ET les réponses HTML (les assets du moteur ne sont jamais du HTML). Budget d'envoi GPU : 2 par frame (`MAX_ASSET_UPLOADS_PER_FRAME`), à régler sur mesure avec le terrain. Fichier de test livré avec le site : `engine/public/assets/selftest/hello.txt`.
- Assets : l'état `failed` est un ajout d'ingénierie (la spec §279 n'a pas d'état d'erreur). L'état `requested` n'est observable qu'un instant : le téléchargement démarre dans le même appel. Un asset relâché reste utilisable en mémoire (`evictable`) jusqu'à `evict()`, et une nouvelle demande le reprend sans retélécharger.
- Bootstrap : un seul point d'entrée (`engine/index.html` → `src/bootstrap.ts`), paramètre `?engine=legacy|new`, legacy par défaut tant que le nouveau moteur ne peut pas remplacer le jeu. Les autres paramètres et le `#hash` sont transmis à la page legacy (elle lit `#mockroom`). Le nouveau moteur est chargé par import dynamique.
- Les scénarios legacy se lancent sans rien installer ni modifier à la racine : `tools/play.mjs` reçoit Playwright par la variable `PLAYWRIGHT`, pointée sur `engine/scripts/legacy/playwright-shim.mjs`.
- Aucun asset Blizzard : géométrie/textures procédurales ou originales uniquement.
